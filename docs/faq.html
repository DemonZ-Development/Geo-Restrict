❓ FAQ

Things people actually ask in support.

What if the Worker is down?

Three things happen, in order:

  1. The plugin sees the HTTP error or timeout (your connectionTimeoutMs default is 3s).
  2. If directFallbackEnabled: true, the plugin retries the lookup directly against ip-api.com. This sends the IP without a token, which is a privacy consideration. Default is false.
  3. If that also fails (or is disabled), the plugin runs the lookup-failure policy. With blockOnLookupFailure: true (the default in 2.1.0+) the player is blocked with kickMessageLookupFailure. Flip it to false if you want fail-open.

Cached entries continue to work through the whole thing — the cache is on your disk and doesn't care whether the Worker exists.

Where does the player data go?

The player's IP is sent to the Worker on every cache miss. That's unavoidable — geolocation requires the IP. The Worker then sends it to whichever provider answered first. We don't run a central log of who looked up what.

If you don't want to share the public Worker with everyone else, deploy your own (it's worker/src/index.js, ~400 lines, free tier is plenty) and set gatewayToken in your config to match a token in the Worker's GATEWAY_TOKENS secret. Requests without a matching token get HTTP 401.

Can I block a specific ISP without blocking the country?

Yes. Set asnMode: BLOCKLIST and add the ASNs to asns. To find the ASN for a specific ISP, look up an IP from that ISP on a site like bgp.he.net or ipinfo.io — the AS number is right there in the result. Put it in as AS12345 (prefix optional).

My VPN detection keeps catching legit players. What do I do?

Look at the actual ISP names that are getting flagged. If you see something like "Hetzner Online GmbH" being blocked because a player happens to be on a Hetzner VPS at home (rare, but it happens), trim vpnKeywords. The default list is conservative — it only flags well-known VPN/hosting providers — but the threshold depends on your player base.

You can also disable VPN detection entirely with vpnCheckEnabled: false.

Does this work with Velocity?

Yes, on Velocity 3.2.0 or later. The plugin uses the async login event continuation API. If you're on an older Velocity, upgrade — the API it needs was added in 3.2.0.

What about Folia?

Detected at startup. The plugin uses the global region scheduler for the config watcher and the async scheduler for everything else. There's nothing Folia-specific in the rule evaluator — it's just thread-safe maps and concurrent lookups.

Why does the cache file get rewritten so much?

It doesn't, usually. Writes are debounced to one every 5 seconds. A burst of cache writes coalesces into a single disk write. On shutdown, one final synchronous save happens.

If you see constant rewrites, you have a loop somewhere — probably a config file that changes every read (bad permissions, weird editor behavior) and triggers the config watcher.

Can I use my own lookup provider?

Yes, on the Worker side. IP_API_ENDPOINTS and IPINFO_ENDPOINTS accept arbitrary URLs with a {ip} placeholder. Whatever the endpoint returns is parsed by the same logic that parses ip-api.com and ipinfo.io — if your provider returns a different shape, you'll need to fork the Worker.
